## 1. Objectif

Après cette tâche, le schéma du cabinet pilote est découpé en **neuf fragments**
réutilisables (`blocs/*.json`), deux templates de départ les assemblent
(`templates/podologue-complet.json`, `templates/podologue-court.json`), et un
script d'atelier sans dépendance (`outils/composer-schema.js`) produit un
`schema.json` complet, validé par le vrai moteur. Composer le template complet
redonne **à l'octet** `clients/cabinet-01/schema.json`. Un nouveau client part
d'un template, pas d'une page blanche ; le temps de fabrication est mesuré.

## 2. Pourquoi

- **Plafond au sur-mesure** (`docs/projection.md` §8, règle 2) : « sur-mesure
  doit signifier *assemblage de blocs existants + thème*, pas développement
  libre ». Sans ce plafond, chaque vente devient un projet ; la question ouverte
  « temps réel de fabrication d'un template » (`docs/projection.md` §12) reçoit
  ici sa première mesure.
- **« Done for you »** (décision actée, `docs/projection.md` §3) : l'outil est
  d'atelier, jamais vendu, jamais installé. Il vit hors de `formulaire/` et
  hors du paquet.
- **Le moteur n'apprend pas à inclure.** Le formulaire tourne sur la tablette,
  le serveur ne sert que `formulaire/` (`serveur/serveur.py:56`, filtre
  `EXTENSIONS_SERVIES` `serveur/serveur.py:195`). Une inclusion à l'exécution
  exposerait `blocs/` sous la racine web ou ajouterait des requêtes au
  démarrage ; la composition se fait donc **à l'atelier**, et le client reçoit
  un `schema.json` complet, comme aujourd'hui.
- **C9-T2** (`outils/atelier/`, « compose un schéma à partir des blocs, valide,
  produit un aperçu ») s'appuiera sur ce format : les fonctions de composition
  sont exportées pour lui.

## 7. Décisions de conception

Tranchées — ne pas rouvrir :

- **D1 — Forme d'un fragment.** `blocs/<nom>.json`, `<nom>` conforme à
  `^[a-z0-9]+(-[a-z0-9]+)*$`. Objet à clés **fermées**, dans cet ordre :
  `{ "version_fragment": 1, "description": "<phrase française>", "blocs": [ <blocs de schéma, tels quels> ] }`.
  Un fragment porte un ou plusieurs **blocs entiers** du format
  (`docs/schema-formulaire.md` §5.2), jamais un champ isolé : le bloc est
  l'unité de pagination et de rendu. Fichier sous forme canonique
  `JSON.stringify(objet, null, 2) + "\n"`, LF. Vocabulaire : un *fragment*
  (fichier de `blocs/`) contient des *blocs* (au sens du schéma).
- **D2 — Les neuf fragments**, partition exacte des 28 blocs du pilote, dans
  l'ordre :
  | Fragment | Blocs (index du pilote) |
  |---|---|
  | `anamnese` | 0-5 |
  | `examen-statique` | 6-8 |
  | `examen-dynamique` | 9-11 |
  | `examen-bilans` | 12-15 |
  | `examen-complementaire` | 16-17 |
  | `empreintes` | 18 |
  | `chaussage` | 19-20 |
  | `ortheses` | 21-25 |
  | `conclusion` | 26-27 |
  Les blocs sont repris **octet pour octet** : clés de brouillon gelées
  (`familliaux`, `spécialistes`, `symétrique`, `pédieux`, `MDC`, `Isthme`…) et
  `id` gelés par le CSS (`patient_infos`, `patient_info_title`,
  `section_squelettes`, `section_enregistrement_plateforme`,
  `image_empreintes` — `docs/schema-formulaire.md:125-164`) compris. Ces mêmes
  clés valent pour un nouveau client : elles portent le style.
- **D3 — Forme d'une recette (template).** `templates/<nom>.json`, clés fermées
  dans cet ordre : `{ "version_recette": 1, "description": "…", "version_schema": 1, "fragments": ["anamnese", …] }`.
  Noms de fragment conformes au motif de D1, sans doublon, résolus **uniquement**
  dans `blocs/` (pas de chemin, pas de `..`). Un template **n'est pas** un
  schéma : un schéma complet n'existe que dans `clients/<client>/` (ou en
  sortie du script). Raison : une seule source par bloc ; un template-schéma
  dupliquerait 28 blocs à garder égaux.
- **D4 — `outils/composer-schema.js`**, Node nu (aucun `require` hors `fs`,
  `path`, `vm`), commentaires et messages en français :
  - `node outils/composer-schema.js <recette.json>` : écrit le schéma composé
    sur la sortie standard, `{ "version_schema": <recette>, "blocs": <concaténation> }`,
    sérialisé `JSON.stringify(schema, null, 2) + "\n"`. Code 0. Sur refus :
    rien sur la sortie standard, messages sur l'erreur standard, code 1.
  - `… <recette.json> --sortie <chemin>` : écrit le fichier avec le drapeau
    `wx` (**refus si le fichier existe** : le pilote ne peut pas être écrasé),
    exige que le dossier parent existe, et **refuse tout chemin qui se résout
    sous `formulaire/`** (comparaison des `realpath` du parent et de
    `formulaire/`) : le miroir n'est jamais écrit par l'outil. Rien n'est écrit
    si la validation échoue.
  - `--verifier <schema.json>` : valide un schéma complet ; code 0/1.
  - Validation : `formulaire/moteur/rendu.js` chargé en `vm` (patron
    `tests/test_schema_client.js:115-123`) avec un `console` dont `warn`
    collecte ; **un avertissement du moteur est un refus à l'atelier**
    (un attribut inconnu dans un fragment est une faute de frappe).
    S'ajoutent : clés fermées de la recette et du fragment, fragment lu par
    `lstat` (refus d'un lien symbolique), existence sur disque de chaque
    `fichier` d'image sous `formulaire/` (que `cheminImageAutorise` ne vérifie
    pas).
  - `module.exports = { composer, verifier, lireFragment }` sous
    `require.main === module` pour la partie CLI : C9-T2 et le test s'en
    servent.
  - Aucun `assert` : les refus sont des messages accumulés.
- **D5 — Les deux templates**, `version_schema: 1` :
  - `podologue-complet` : les neuf fragments dans l'ordre de D2 (28 blocs).
  - `podologue-court` : `anamnese`, `examen-statique`, `ortheses`,
    `conclusion` (16 blocs, 4 images).
- **D6 — Aucune grille dans `blocs/` ni `templates/`.** Les trois conditions de
  `docs/schema-formulaire.md:481-501` se remplissent **client par client**,
  dont un export sur la tablette du client : un template n'est pas un client,
  et une grille de bibliothèque partirait sans épreuve. La seule grille connue
  dérive de la fiche du prospect, interdite au dépôt. Une grille entre dans le
  `schema.json` d'un client, en version 2, après ses trois conditions.
  Garde B6.

## 10. Points de sécurité à l'attention de l'auditeur

- **Écriture de fichiers** : `--sortie` écrit sur le poste d'atelier ; refus
  d'écraser (`wx`) et refus de `formulaire/` (via `realpath`). Ne s'exécute
  jamais chez un client.
- **Surface exposée** : nulle. `blocs/`, `templates/`, `outils/` sont hors de la
  racine web (`serveur/serveur.py:56`) et hors du paquet (B7).
- **Lecture de fichiers** : noms de fragment ancrés sur un motif sans `/` ni
  `.` ; liens symboliques refusés (`lstat`).
- **Confidentialité** : le dépôt est public. Aucun fragment ni template ne porte
  d'identité de cabinet (gardé par `tests/test_identite_absente.py`) ni rien de
  la fiche du prospect (gardé par `AucunMarqueurDeLaFiche`, seulement sur le
  poste qui la détient : A14 se joue là). Le client fictif n'emploie que le
  vocabulaire D9. L'implémenteur **ne lit pas** `fiche_presentation.html`.
- **Données de santé** : aucune. Pas de journalisation, pas d'authentification.
- **Production** : la seule voie vers la tablette resterait un `schema.json`
  écrit dans `clients/` puis empaqueté ; A1 garantit que le pilote n'a pas
  bougé.
